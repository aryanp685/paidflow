## Dependencies and authority

`001` defines customer/history and composite tenant references; `002` enables tenant RLS, read and legacy write policies/grants; `005` supplies creation audit and timestamps; `010` defines request ledger and creation RPC. `012`–`015` depend on these and apply in numeric order; `013` replaces 012 RPC, `015` replaces both again, so review the **final** definitions. Functions use fixed `search_path=pg_catalog,pg_temp` and qualified app/auth names; role checks use `paidflow_private.require_business_role`. `tests/database/run-tests.mjs` tests owner, manager, accountant/outsider, cross-tenant requests, ordinary grants and hardening. The mock functions are owned by the local superuser (therefore bypass RLS); `final replacement RPCs retain expected owner privileges and hardened search paths` asserts mock owner/grants. Real migration-owner role, membership inheritance, default privileges, BYPASSRLS, trigger ownership, PostgREST grants and provider role configuration are **NOT TESTED**; do not assume the mock matches a provider. Security definers must have only deliberate owner authority. Role-based authorization and not client controls is necessary; alternate privileged writers remain unenumerated.

Upgrade exercised sequentially against synthetic existing duplicates and invoice counts, not a real production copy. Transactional application, interrupt recovery, migration runner behavior on a real provider, dependency/index duration and rollback are **NOT TESTED**. Down-migration cannot simply drop `edit_version` or restore old grants safely while new clients are live; doing so loses CAS and audit guarantees. Detailed compatibility, prerequisites and rollback are in `customer-grant-compatibility.md`.

No full cross-section reconciliation guarantee; use an independently reviewed single-snapshot reader before claiming consistency. No financial RPC contracts changed.
