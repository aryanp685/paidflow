# Local payment recording and void history

This is local implementation and testing only, not a deployed or financially/security-approved feature. It records a user's statement of payment, not a transfer or independently verified receipt. The UI does not upload, download, preview or associate proof.

- Authorized owner, admin, manager and accountant can record a no-proof partial or full payment on an already-issued invoice. The action validates decimal amounts as integer paise and uses the active server-derived business. It always passes a null proof ID. Owner/admin can void a payment with a reason and explicit confirmation. Voiding preserves the original record and restores invoice balance. A repeat void returns the existing record and does not replace its original reason.
- History and detail queries are business-scoped, show void status/reason, fail on query errors and use stable date/ID pagination. The current interface exposes at most the first 50,000 history records.
- A same-tab request key is kept in session storage until success is received. Retry *the exact same fields* after uncertainty, including optional reference and notes. Inputs themselves are not retained, and separate tabs/devices/new keys cannot prevent duplicate real-world payments. Check history before submitting a new request. A replay of a voided payment does not create a replacement payment.
- The existing database RPC locks the invoice and compares the key and exact parameters before updating payment, balance and audit atomically. The business-wide unique key prevents duplicate rows, but concurrent reuse of one key on different invoices can surface a uniqueness error rather than a clean mismatch response; the UI surfaces a generic error. This was a code review observation, not a real-provider concurrency verification.
- Null proof in the app is **not a security boundary**: authenticated clients can call the base RPC directly. The local proof hold migration `20261107000700` must be applied and verified with the schema before the RPC is exposed; it is not yet applied to hosted Supabase. Known base-schema unscanned-proof vulnerabilities remain a security acceptance failure. The hold is not scanner verification.
- Candidate issuance hold `20261107000900` prevents new issuance via ordinary writes and RPCs when installed. Thus this payment flow is only usable with pre-existing issued invoices under that hold; drafts cannot be issued. GST/rounding and financial rules still need expert review. A privileged actor can bypass ordinary trigger protections.
- Tests exercise synthetic isolated PostgreSQL with mock Supabase auth, and mocked frontend/server actions. Real Supabase Auth, RLS/PostgREST integration, production data and deployment have not been verified. Review roles, history, financial correctness and protections in the actual target before launch.

## Forced cross-invoice same-key race — synthetic only

A local mock-Supabase test now deliberately waits on an uncommitted unique key across two issued invoices. One transaction commits one payment and audit event; the other fails `23505`, rolls back with its invoice unchanged, and later retries fail with the existing `22023` mismatch. This confirms the previously reviewed exception behavior under this synthetic scenario, not clean user-facing idempotency or real Supabase behavior; no financial RPC contract changed.
