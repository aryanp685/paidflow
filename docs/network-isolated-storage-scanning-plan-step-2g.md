# Step 2G — Network-isolated storage and malware-scanning pilot plan

**Date:** 7 November 2026. **Status: plan only; pilot not authorized to start.** No Garage, scanner, signature database or alternative emulator was installed or run. No application code, existing migration, dependency manifest or lockfile was changed. No cloud service, paid service or customer document was used. The current emulator is unchanged. The only Step 2G repository deliverable is this document.

**Safety gate:** the pilot must not start until separate approval **and** its complete isolation checks in section E pass on the machine where it will run. A network-namespace primitive was demonstrated in this sandbox, but a full pilot boundary has not been built or validated; this is not approval or evidence that running the proposed stack is safe here. If any gate fails or cannot be independently verified, stop without starting the pilot.

## A. Garage pilot architecture

### Candidate and constraints

Garage is the Step 2F first-choice **candidate**, not an approved replacement. The [v2.5.0 release/tag](https://github.com/deuxfleurs-org/garage/tags) and [current quick start](https://garagehq.deuxfleurs.fr/documentation/quick-start/) show active development. Its upstream [release process](https://garagehq.deuxfleurs.fr/documentation/development/release-process/) lists Linux aarch64 and x86-64 artifacts, not a native macOS binary. On Apple Silicon, plan an **ARM64 Linux guest VM**, with no network adapter and no host port forwarding. Verify the chosen pinned Linux ARM64 artifact, provenance, digest/signature, current advisories and AGPL-3.0 implications before any authorized import; this plan does not download or install it. Architecture support and operation on the user's Mac are not independently tested.

Suggested topology, entirely inside a throwaway isolated guest:

```
synthetic test/browser --> local app --> local PostgreSQL
                               |            ^
                               v            | scan result / audit
                    Garage S3 127.0.0.1     isolated worker
                      private buckets <----- scan stream --> clamd Unix socket
```

* Configure Garage S3 `api_bind_addr` on **127.0.0.1 only**, RPC `rpc_bind_addr` and its advertised address on **127.0.0.1 only**; single-node, no bootstrap peers or discovery. Validate exact fields and single-node setup against the chosen pinned release. Disable S3 website, admin/metrics and all unneeded endpoints; if a required control cannot be disabled, bind it only to guest loopback and protect it with a separate temporary credential. Bind IPv6 only if required and only to `::1`; otherwise disable IPv6 listeners. No host publication, container `-p`, tunnel, reverse proxy, port forward, shared network socket or outside access. Confirm each actual listener, not only intended config. The official [sample config](https://garagehq.deuxfleurs.fr/documentation/reference-manual/configuration/) uses wildcard binds: **do not copy those binds**.
* Create disposable distinct quarantine and approved buckets, and distinct identities/permissions for intake, scan worker and the trusted promotion/download service. Provisioning/owner credentials are used only for setup, not held by ordinary app requests. Grant minimum Garage per-key/per-bucket read/write access and validate denied operations; disable website access. Garage does not implement S3 bucket policies, ACL authorization or S3 public-access-block in the AWS sense, and its bucket-level read/write grants cannot enforce arbitrary prefix or fine-grained PUT-versus-DELETE separation. It also lacks bucket versioning. Do not assert prefix isolation or immutable versions from those APIs. Separate buckets and process credentials; if the desired role separation cannot be expressed or independently verified, stop rather than weakening it. Tenant ownership is independently enforced by trusted authorization and tenant-safe database policies.
* Use a fresh random key for every object, never a user-supplied path. Only the trusted promotion component may write approved objects; no untrusted party receives Garage credentials or a direct download URL. An app-layer no-overwrite rule is not a Garage immutability guarantee: treat storage/worker compromise as outside that guarantee, restrict writers, check hashes, and fail if the required immutability is not enforceable. Delete/cleanup requires separate controlled procedures.
* Garage [documents](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/) PUT, GET, DELETE, multipart and presigned URLs, but no S3 bucket policy/versioning. Use path-style requests and the configured region; treat docs as claims until tested. The **current** `storage-lab/s3.mjs` expects the S3rver-only token header and its `assertPrivate` requires a 403 response on the service root; neither constitutes a general Garage adapter or private-bucket proof. Make a separate pilot adapter only after approval; retain the existing emulator and its tests.
* Test presigned PUT/GET, expiry, tampering, wrong key and wrong method **only with synthetic objects inside the guest**. Presigned URLs are bearer secrets. Passing those tests does not justify using them for customer downloads: they bypass a per-request membership/status check and generally cannot be individually revoked promptly. The proposed application download path proxies bytes instead. Do not print, persist or audit presigned URLs.

**Installation/resource requirements:** an independently obtained, pinned compatible Linux ARM64 Garage binary and its prerequisites, disposable metadata/data directories, a private random RPC secret and isolated local storage capacity are required. Never use host-wide installation locations or a shared data directory. Selection and offline staging of binaries are separate approval steps; exact package availability, signatures, checksum and operational requirements remain to be verified. A one-node test instance has no meaningful redundancy and is not a production configuration.

## B. Malware-scanning architecture

### Engine and signature updates

Choose maintained [ClamAV/clamd](https://docs.clamav.net/) for the first proposed local pilot. The vendor supplies a universal macOS installer and Linux options ([installation](https://docs.clamav.net/manual/Installing.html)); this design uses Linux ARM64 inside the no-NIC guest for a stronger boundary. Check supported versions, licensing, artifact provenance and advisories at the time of the separately approved pilot. Neither engine nor signatures are installed yet.

ClamAV needs a loaded signature database. [FreshClam](https://docs.clamav.net/manual/Usage/Configuration.html) normally accesses external update services; running it online inside this pilot is prohibited. If separately approved, a distinct staging process on a separately controlled machine may obtain official signed full CVD files and engine artifacts **before** the pilot, verify vendor signatures/digests, compatibility, creation time and provenance, then transfer via a reviewed read-only offline image. Detach that image after import. Do not transfer customer data or credentials. The guest remains offline throughout; do not attach a network to update. CVDs are vendor-signed ([terminology](https://docs.clamav.net/appendix/Terminology.html)); validate the exact verification method for the selected build, do not rely on a checksum from the same untrusted source alone. No update transfer has been authorized or performed. If no trustworthy fresh signatures are available, the scanner remains unavailable and downloads stay denied.

Define signature age, the trusted clock/source, grace policy, event schedule and operator ownership **before implementation**. Use a provisional pilot threshold of 24 hours from a verified database generation timestamp only if feasibility is approved; a fixed threshold is an engineering choice, not a vendor guarantee. If the clock, definition provenance or freshness cannot be established, fail closed. Detect engine/database incompatibility and failed reloads.

### Proposed quarantine-first state machine

1. Authenticate and authorize the actor, business and area before reading file contents; limit each actual streamed upload to the current **5 MiB** maximum, independent of the declared length. Create a durable upload attempt and event. Accept only PDF, PNG or JPEG after type and conservative structural inspection. This inspection alone is not a scan.
2. Store an object under a server-generated random key in a private quarantine bucket. Create a durable idempotent job binding tenant, document, object identity, expected size and SHA-256. Deny all browser-facing reads from quarantine. Avoid executing files, using unsafe extensions or running active content. No file contents enter logs.
3. A separate least-privilege worker with read-only quarantine permission reads exact bytes, hashes the actual stream, and sends them via permission-restricted **Unix socket** to isolated clamd using [INSTREAM](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). Do not run a publicly reachable TCP scanner. Isolate worker/scanner identities and filesystem; no outbound network. Limit CPU, RAM, disk, queue, concurrency and job lifetime; terminate and quarantine on OOM, crash, partial read, worker disconnect, cancellation, malformed result or timeout.
4. Set initial pilot limits to one concurrent scan, **30-second** wall-clock timeout and maximum input **5 MiB**; configure `StreamMaxLength` and `MaxFileSize` at least 5 MiB and a bounded decompressed `MaxScanSize` (initially 25 MiB), recursion and member-count ceilings, subject to verification against the pinned scanner. Explicitly enable/test `AlertExceedsMax` and encrypted-content alerts where supported. [ClamAV warns](https://docs.clamav.net/manual/Usage/Scanning.html) oversized files can be skipped and assumed clean; limit, parser, encrypted, timeout and incomplete indications must map to **inconclusive**, never pass. Reject unsupported/password-protected/encrypted or uninspectable files; no passwords are requested or retained in this pilot. Remove file-type bypasses and fail closed if coverage cannot be determined.
5. Record an append-only attestation: tenant/document and job ID, immutable quarantine object identity where available, SHA-256 and byte count of the actual stream, engine identity/version, **loaded** signature generation/digest, scan policy/config version, timestamps, result (`no_detection`, `detected`, `incomplete`, `error`) and reason code. A scanner non-detection is not a guarantee of safety. Bind the engine generation unambiguously: pin a scanner process to one verified definition set during each scan, or use an engine-supported generation mechanism. Do not infer that a separate `VERSION` query proves the scan used that generation if reload can race. Stop admission during controlled reload, drain workers or start a fresh process; if generation is ambiguous, result is inconclusive.
6. Only `no_detection` with complete structural validation and a matching current attestation permits promotion to a private approved object with a new unique key. Verify promotion bytes and SHA-256 before recording readiness; lock the row, compare current source identity, size/hash, generation, policy and status again before commit. Prevent overwrites by limiting approved-bucket writers to the trusted promoter; reconcile stale jobs and orphan objects after crashes. Database/object storage are not atomic: durable attempt/outbox records and idempotent reconciliation are mandatory; no promotion failure may produce an accessible object.
7. Definition or scan-policy generation changes put previous results into a stale/blocked state **before** new access, invalidate new grants, queue rescans, and reopen only after current complete non-detection. If a later detection occurs, block access immediately and preserve the detection and history. Record attempts, retries and results. If refresh cannot be safely completed offline, access stays blocked. An always-current-signature policy may harm availability; this strict policy needs explicit approval and operational ownership.

## C. Download fail-closed policy and existing synthetic data

### Existing behavior verified by source inspection

`storage-lab/core.mjs` currently permits both `structurally_valid_unscanned` and `verified` in **both** `grant` and `download`. The latter checks session, a session-bound 60-second grant, document access via `storage_lock`, stored byte length/SHA-256 and re-inspects the content, but none of those is malware scanning. The route `src/app/api/storage-lab/documents/[id]/route.ts` calls these paths for POST grants and GET downloads/previews. A synthetic, structurally accepted file can therefore be downloaded without a scanner. `verified` also currently can be minted by privileged test fixtures; its label alone is not evidence of an authentic scan.

### Proposed rule (not yet implemented)

**Deny every grant, original download and preview unless all of the following hold:** (1) live verified session and active membership with area-specific role; (2) document is neither deleted, quarantined, revoked, held nor stale; (3) a complete non-detection attestation exists from the designated trusted scanner and current allowed engine, signature and policy generation; (4) the attestation matches tenant, document, byte length and exact approved object digest/identity; (5) the scanner health/availability and signature freshness policy is satisfied at decision time; and (6) the approved object is still the same bytes. Unknown, missing, error, timeout, expired, unsupported, encrypted, failed scans, stale signatures, scanner unavailable, attestation mismatch or storage errors all deny. Do not return a presigned storage GET. Recheck authorization, hold, current scan generation and object identity on the actual download, not only grant creation; use non-enumerating failure responses and `no-store`. For the current 5 MiB limit, buffer and hash the exact response bytes before returning any of them, rather than streaming unchecked bytes. Define and test revocation/delivery race semantics: serialize access decision against state changes and prevent new deliveries after a hold is committed; bytes already delivered cannot be recalled.

The availability requirement is deliberately stricter than simply trusting an old attestation: even a previously scanned file is unavailable while the scanner/required definition generation is unhealthy or cannot be established. This may halt all downloads during maintenance or long offline periods; do not weaken it silently.

### Migration and payment-history impact

* All existing synthetic `structurally_valid_unscanned`, `legacy_unverified`, quarantine, and old `verified` fixture documents have **no trustworthy scan attestation** and become inaccessible under the proposed predicate. Preserve their existing history; rescan eligible synthetic objects or recreate them. Do not relabel them as scanned. Tests that currently expect an unscanned download must explicitly be rewritten to expect denial; tests that require a successful download need a real scanner result, not a privileged DB fixture.
* Current proof trigger in `storage-lab/migrations/20261107030000_proof_lifecycle_and_scan_state.sql` checks `verified` and prevents deletion or revocation of proof linked to **any** payment or extraction. A newly detected linked proof therefore cannot simply transition to `revoked` under existing rules. Plan a **separate access/security hold** that denies download and future proof use while retaining the object and all historical links. Do not delete, rewrite or retroactively invalidate payments or extraction history.
* An additive DB enforcement change for **new or context-changing** payment-proof attachment would be required to require a current matching scan attestation/hold check, not just `verified`. This changes acceptance of non-null proof even though the payment RPC signature/JSON and null-proof contract remain unchanged; it requires explicit approval, an exact contract note, same documented error behavior where feasible, and replay/concurrency regression tests. Idempotent replay of historical payments must remain unchanged, and unrelated updates/voids must not revalidate old proofs. Preserve the existing row-lock ordering and retention semantics. Do not change financial code or trigger during this planning step.
* Any additive migration is **local-pilot only** and must not modify the six original Supabase migrations or existing Neon/Better Auth/storage migrations. Never apply it to an existing cloud database.

## D. Document audit schema and events

Propose an additive append-only `document_security_events` table and restricted security-event sink; final naming/schema requires review. Include event UUID, UTC timestamp, correlation and idempotency IDs, event type/schema version, server-derived tenant/document IDs when safely known, verified actor ID or explicit anonymous/system actor, outcome, allowlisted reason code, area and non-sensitive scan engine/signature/policy generation as applicable. A tenant is never taken on trust from the request. Keep event payloads typed and bounded, not arbitrary client JSON.

| Lifecycle | Required event(s) | Minimum semantics |
|---|---|---|
| Upload | `upload_initiated`, `upload_completed`, `validation_failed` | Attempt begins after identity context established or in restricted anonymous sink; completion only when stored in quarantine, not when scanned. Include abort/oversize reasons. |
| Scan | `scan_started`, `scan_passed`, `scan_failed` | `scan_passed` means complete non-detection with exact-byte attestation, not malware-free; `scan_failed` distinguishes detection, unavailable, timeout, unsupported, encrypted and incomplete. Include rescan generation and correlation. |
| Download | `download_authorized`, `download_denied` | Authorization is not delivery; optionally record `delivery_completed` or `delivery_failed`, without storing response bytes. Deny also logs scanner outage/stale attestation with safe reason. |
| Revocation / hold | `access_revoked`, `access_hold_applied`, `access_restored` | Record trusted actor/system and safe cause; linked proof is held, not deleted or retroactively invalidated. |
| Deletion | `deletion_attempted`, `deletion_failed`, `deletion_completed` | Distinguish initiation from storage completion; record retry correlation and preserve payment/audit history. |
| Cross-tenant | `cross_tenant_denied` | Store in a privileged security sink, not in attacker's tenant feed; do not leak target existence or another tenant's metadata through response/audit views. Unknown targets use a generic reason. |

Tenant-scoped readers use RLS and least privilege; insert through narrowly scoped server/worker functions only; prohibit ordinary UPDATE/DELETE and keep retained history with controlled backups. Privileged administrators can still alter a database: evaluate stronger external tamper evidence separately, without claiming append-only is absolute. Successful state mutation and event/outbox commit together. Denied actions often roll back their normal transaction, so use a separate durable, restricted append path that survives rollback. Define backpressure and a fail-closed policy if a required audit record cannot be persisted, including bounded queue/recovery; do not block the attack-response path indefinitely or leak information. Audit event ingestion needs its own authorization, spoofing and availability tests.

Never log or return file contents, raw request bodies, passwords, cookies/session IDs, auth headers, access/secret keys, signature databases, presigned URLs/grants, untrusted filenames, object paths, or arbitrary exceptions. Do not place file hashes in broadly visible event metadata; keep exact-byte hashes in restricted attestations. Configure application, worker, database, request, proxy and service logs together, disable secret-bearing query-string logging, and test actual logs—not just the audit table. No logs are a substitute for RLS.

## E. Network isolation procedure and verified limits

### Observed in this sandbox, no server started

* `unshare -n true` returned **exit 1, Operation not permitted**.
* `unshare --user --map-root-user --net true` returned **exit 0**. In a further `--user --map-root-user --net --mount --fork` probe, the network namespace ID differed from the caller, `ip -brief link` showed only `lo`, IPv4/IPv6 route tables were empty, and after enabling loopback no route existed to `192.0.2.1` or `2001:db8::1`. A TCP connection and UDP send to the documentation-only IPv4 address returned `ENETUNREACH`. A temporary 1 MiB tmpfs mount in that mount namespace succeeded, was unmounted, and its empty directory removed. An initial UDP probe had a test-script argument error; the corrected probe produced the stated results.
* This supersedes Step 2F's narrower observation that plain `unshare -n` was denied. It proves only these primitives in this sandbox at that moment; the namespace was torn down. It does **not** prove complete pilot filesystem, IPC, inherited-file-descriptor, user, host, browser, hypervisor or cloud-credential isolation. It does not establish that Apple macOS supports Linux `unshare` (it does not natively). Docker/Podman and Garage/ClamAV were absent on PATH; no installs attempted. Environment variable **names** indicated GitHub tokens exist in the parent environment; values were not printed. They must not be inherited by a pilot.

### Required preflight on the actual machine — abort if any item fails

1. After separate authorization, use an existing or separately approved disposable Linux ARM64 VM with **no virtual NIC**, no NAT/bridged/host-only adapter, no port forwarding, and no Docker daemon host networking; perform tests from the guest itself. Disable host/guest shared folders, host filesystem mounts, clipboard/drag-drop, SSH/agent forwarding, guest proxy channels, shared sockets and unrelated device passthrough. A display console alone must not imply a network route or mount. Linux namespace option may be used inside a suitably isolated Linux environment, but ordinary namespaces alone share the host filesystem and may allow access to host Unix sockets; do not treat `unshare -n` alone as an isolation solution.
2. Start with only a new guest disk/snapshot, reviewed system tools and a sanitized copy of the PAIDFLOW files required for the pilot. Exclude `.env*`, `.git` credentials/config, all home-directory cloud credential stores, host SSH agents, unrelated repositories and unreviewed sockets. Use a temporary guest HOME and `env -i` with a small explicit allowlist of nonsecret variables; disable SDK credential discovery/metadata services and telemetry. Credentials are random, synthetic, scoped to this guest, stored only in private ephemeral files/memory, not command-line arguments, logs, Git, or shared directories. Verify environment variable **names** and mount listings without disclosing any values. No production credentials are imported.
3. Stage reviewed dependencies, PostgreSQL, Garage, scanner and definitions only after separate approval via an integrity-verified read-only offline image. The image contains no host projects, credential stores or private config; unmount/detach it after copying. No package-manager, DNS, telemetry, cloud, signature-update or other network operation from the guest. If necessary artifacts or trustworthy signatures cannot be made available offline, stop rather than adding a network adapter. Never access Neon, Supabase cloud, R2, Vercel or any other cloud service from the pilot.
4. Before starting services, inspect virtual NIC inventory, IPv4/IPv6 interfaces and routes, DNS/resolver settings, mounted filesystems and socket/IPC exposure; confirm only guest loopback exists, no default or external routes, no shared host path, proxy, agent or inherited descriptor. Check external TCP, UDP and DNS attempts fail, including host gateway and both address families; verify host cannot reach guest ports. Prove isolated loopback within the guest works using only a disposable test service once authorized. Verify filesystem reads of unrelated project/credential canaries fail, without trying to access real secrets. If any check fails or cannot be verified, **stop**.
5. Start only the pilot services after the gate passes; inspect real listen addresses and verify Garage S3/RPC are **loopback-only**, clamd is Unix-socket only and no admin/web ports are exposed. The existing Next browser test binds `0.0.0.0`; do not run it against a shared host or preview proxy. Adapt or run it entirely inside the no-NIC guest only if the entire VM boundary is validated and no ports escape; validate its actual listener. A forged HTTP Host header is not a network isolation control. Repeat preflight after restart, configuration change, or VM update, and log only redacted evidence.

This environment has not proved that all items can be met, and no guest has been created here. **No fallback to a publicly exposed preview or weaker isolation is permitted.**

## F. 8 GB Apple Silicon resource plan

No resource figures below are local measurements. Garage is described as lightweight; the exact pinned ARM64 process/guest memory and disk have not been measured. Its documented LMDB map size is virtual address space, not necessarily resident RAM ([configuration](https://garagehq.deuxfleurs.fr/documentation/reference-manual/configuration/)). ClamAV recommends **3 GiB or more** RAM and **5 GiB free disk** ([requirements](https://docs.clamav.net/)); its [Docker guidance](https://docs.clamav.net/manual/Installing/Docker.html) recommends 3 GiB minimum/4 GiB preferred and notes concurrent database reload can temporarily double engine memory. Guest OS, PostgreSQL, Next, browser, Garage, scan workload, VM overhead, page cache and macOS must fit in the **same physical 8 GB**.

| Item | Planning allowance / status |
|---|---|
| macOS and other host work | Reserve at least roughly 2–3 GiB; actual memory pressure varies and must be measured. |
| Linux ARM64 guest, whole VM | Trial cap 5 GiB, leaving only ~3 GiB for host and hypervisor; **not a guaranteed feasible configuration**. Guest OS, services and page cache are included in this cap, not added to it again. |
| ClamAV within VM | Budget vendor minimum 3 GiB, with reload headroom; this leaves little room for the rest. One worker, no concurrency; possibly use `ConcurrentDatabaseReload no` after verifying behavior, with downloads denied while unavailable. |
| Garage, PostgreSQL, Next, tests, guest OS | Share the remainder. No credible per-process peak estimate exists without a benchmark; avoid running browser and Next unnecessarily alongside scans. |
| Disk | At least ClamAV's 5 GiB free-space guidance plus guest OS, database, artifact image, test objects, logs and temporary files. Set disposable-volume quotas and measure. |

Measure idle/peak VM and host resident RAM, compressed memory, swap, CPU and disk during scan, signature reload, 5 MiB boundary, failure/retry and browser/DB tests. Agree thresholds before execution; suggested aborts: OS memory pressure becomes critical, swap rises continuously, OOM occurs, guest is unstable, or security processes are killed. If stable isolation plus scanning is infeasible on 8 GB, stop and report; do not lower limits in a way that yields incomplete scans as passes. Sequential phases may reduce peak load, but an app scan/download integration test requires its components together.

## H. Cleanup and rollback

* Before pilot, capture hashes of manifests, lockfile and every existing migration; use only disposable isolated data. Preserve the original emulator and current work. Record exact guest/process/disk identifiers without exposing secrets.
* Stop scan intake, revoke temporary test grants and keys, stop application, workers, clamd, Garage and PostgreSQL gracefully, then shut down the guest. Verify process/listener absence and no host port forwards. Detach reviewed artifact media. Destroy **only** the uniquely identified disposable guest disk, temp buckets, data directories, keys and test database; do not run a broad deletion command against the repository, home directory or unrelated projects. Verify deletion and confirm manifests/migration hashes unchanged.
* If later code work is approved, keep it isolated behind an explicit non-production pilot configuration; baseline S3rver remains available. Roll back the pilot by disabling it and discarding the disposable DB/VM, **not** by editing/deleting existing migrations or resetting the working tree. Review planned new files and revert only explicitly approved changes without overwriting prior user work. Production is outside scope.
* Security rollback must not restore unscanned access in any environment that holds real data. If disabling scanner integration would re-enable the existing unscanned-download behavior, leave downloads disabled rather than falling back; this is a design requirement, not yet implemented. Preserve audit/payment history and prevent a failed cleanup from marking deletion complete.
