# Supabase recovery verification — current local work

## Scope and current status

PR #2 was merged and promoted to production as `30cfb7625502fd856ec08bbaa407740dc80eb68e`. The app-level password recovery form and legacy reset action remain disabled; callbacks explicitly labelled recovery are rejected. This is a mitigation, not a provider-verified recovery implementation. A caller can alter or omit the `flow` label and the application still cannot independently classify a PKCE code's provider purpose. Existing provider sessions and APIs are not disabled by this app change.

This branch prepares an additional callback fix but is **not deployed**. It forwards a syntactically valid, unique `sb_flow_id` to the server SDK and rejects malformed or duplicate flow IDs before exchange. Requests without that ID retain the legacy verifier behavior for compatibility. A flow ID is untrusted, selects a verifier slot and **does not authenticate the recovery purpose**.

## Concrete SDK finding: opt-in is not enabled

The installed `@supabase/auth-js` / `@supabase/ssr` code stores per-flow verifier slots and a legacy key containing the most recent verifier. The server cannot infer the flow ID from the browser URL; the application must pass it explicitly. However, the SDK only appends `sb_flow_id` to redirect URLs when `auth.experimental.appendPkceFlowIdToRedirects` is enabled. The current app does **not** enable it. Two simultaneous signup/verification flows can therefore still select the wrong legacy verifier. The callback change helps only when a flow ID is actually present. We deliberately did not enable the opt-in: SDK documentation warns that additional query parameters may break exact redirect-allowlist entries. Provider allowlist, email templates and redirect behavior have not been tested.

The SDK's returned `redirectType` is derived from locally stored verifier metadata (`/recovery`), not independently authenticated by the provider response. An offline test demonstrates that changing only this metadata changes `redirectType` while sending the same verifier. Do not use it as authorization to update passwords. Passing a flow ID does not make a callback a trusted recovery callback, and retaining the legacy no-ID path leaves the multiple-flow limitation unresolved.

## Provider source inspection, not provider integration

For preliminary design only, the official Supabase Auth source at tag `v2.197.0`, commit `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`, was read via GitHub API. It is not evidence of the hosted project's actual version, settings or behavior.

- In `internal/api/recover.go`, a PKCE recovery request creates a flow state with the recovery authentication method. `internal/api/token.go` checks the code, expiry and verifier, then issues a session and destroys the flow state. Concurrent one-time behavior must still be tested with a real instance; source inspection alone is not proof.
- In `internal/api/verify.go`, the `GET` PKCE path parses a verification type before issuing an auth code. Its `POST` verification path issues a session using `models.OTP`; token-hash lookup for `signup` and `recovery` uses different token categories, but generic email verification can consider both. A design based on signed AMR claims must therefore first prove the exact path, claim values, freshness, provider version and session/revocation semantics. Do not assume every recovery session contains a distinct `recovery` AMR.
- The token service associates authentication method claims with a session and calculates JWT AMR; that is a candidate for investigation, **not** a verified solution. A secure design must establish token signature/issuer/audience, user and session binding, freshness, one-time/replay semantics, and access restrictions in the presence of refresh, other sessions, password change and logout.
- An official `v2.197.0` Linux release exists, but its asset download redirected to a host unavailable in this sandbox. No Auth binary was obtained or run. Docker/Podman/Supabase CLI, Go, PostgreSQL and Chromium are not installed here. No hosted project, credentials, configuration or data was accessed. The attempted release asset fetch failed; it was not a successful provider test.

## Test evidence and limitations

The added `tests/unit/supabase-pkce-sdk.test.ts` uses the **installed real SDK and SSR cookie adapter**, but replaces the Auth HTTP provider with a synthetic in-memory transport. With the SDK's experimental flow-ID setting enabled in the test only, it exercises two concurrent signup verifications out of order, missing slots and replay. It also demonstrates that the current default without the setting uses the latest verifier and that local metadata controls `redirectType`. Replay behavior belongs to the synthetic transport and must not be attributed to Supabase Auth. Callback argument/invalid-ID tests mock the server client.

Earlier auth-focused offline run: 13/13 hold checks and 41/41 unit tests passed in the network-isolated namespace/chroot. After the subsequent local audit changes, the same runner passed 13/13 hold checks and 50/50 unit tests. Lint, typecheck, the loopback-only isolated production build, `git diff --check`, and production-boundary checks (5/5) also passed. The optional encrypted-PDF fixture was absent and its eight structural probes were skipped. This is not a real Supabase Auth, browser or production test. No database migration, scanner, Garage or financial logic was changed.

## Next real-provider gate

Provision or provide an independently verified **disposable local Supabase Auth test stack**, isolated from external network/host sockets/credentials, with disposable PostgreSQL, synthetic keys and a private synthetic email capture; verify provenance and listeners. Do not create cloud resources or use a customer's project. It need not be the no-NIC malware-pilot VM; scanner/Garage gates remain separate and unchanged.
2. Establish exact Auth version/config and build the test matrix: signup vs recovery and cross-account code/token substitution; tampered/missing/duplicate flow IDs; simultaneous flows and provider redirect-allowlist exact matches; invalid/expired/replayed links and concurrent redemption; password changes, refresh, logout and all-session revocation; suspended/unverified/deleted members; cookie flags, origin checks, no-store headers and logs without tokens.
3. Compare JWT-signature-verified claims and session IDs for PKCE recovery and token-hash POST verification against signup, normal login and refresh. Test provider secure-password-change settings and direct API calls. Choose a purpose/session binding approach only after its assumptions pass actual provider tests; never trust a client-chosen flag, local redirect metadata or an unverified JWT.
4. Only after these tests and security review, decide whether to enable the SDK flow-ID option with a verified redirect allowlist, and whether a recovery workflow can be safely enabled. Keep the current app recovery block and document download/preview hold in place until their respective acceptance gates pass.
