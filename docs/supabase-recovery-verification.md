# Supabase recovery verification — current local work

## Scope and current status

PR #2 was merged and promoted to production as `30cfb7625502fd856ec08bbaa407740dc80eb68e`. The app-level password recovery form and legacy reset action remain disabled; callbacks explicitly labelled recovery are rejected. This is a mitigation, not a provider-verified recovery implementation. A caller can alter or omit the `flow` label and the application still cannot independently classify a PKCE code's provider purpose. Existing provider sessions and APIs are not disabled by this app change.

PR #3 was merged and deployed in production as `0ce31ccc7e866add30988f60297c4b78767a5b79`; its callback change forwards a syntactically valid, unique `sb_flow_id` to the server SDK and rejects malformed or duplicate flow IDs before exchange. Requests without that ID retain the legacy verifier behavior for compatibility. A flow ID is untrusted, selects a verifier slot and **does not authenticate the recovery purpose**.

## Concrete SDK finding: opt-in is not enabled

The installed `@supabase/auth-js` / `@supabase/ssr` code stores per-flow verifier slots and a legacy key containing the most recent verifier. The server cannot infer the flow ID from the browser URL; the application must pass it explicitly. However, the SDK only appends `sb_flow_id` to redirect URLs when `auth.experimental.appendPkceFlowIdToRedirects` is enabled. The current app does **not** enable it. Two simultaneous signup/verification flows can therefore still select the wrong legacy verifier. The callback change helps only when a flow ID is actually present. We deliberately did not enable the opt-in: SDK documentation warns that additional query parameters may break exact redirect-allowlist entries. Provider allowlist, email templates and redirect behavior have not been tested.

The SDK's returned `redirectType` is derived from locally stored verifier metadata (`/recovery`), not independently authenticated by the provider response. An offline test demonstrates that changing only this metadata changes `redirectType` while sending the same verifier. Do not use it as authorization to update passwords. Passing a flow ID does not make a callback a trusted recovery callback, and retaining the legacy no-ID path leaves the multiple-flow limitation unresolved.

## Provider source inspection, not provider integration

For preliminary design only, the official Supabase Auth source at tag `v2.197.0`, commit `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`, was read via GitHub API. It is not evidence of the hosted project's actual version, settings or behavior.

- In `internal/api/recover.go`, a PKCE recovery request creates a flow state with the recovery authentication method. `internal/api/token.go` checks the code, expiry and verifier, then issues a session and destroys the flow state. Concurrent one-time behavior must still be tested with a real instance; source inspection alone is not proof.
- In `internal/api/verify.go`, the `GET` PKCE path parses a verification type before issuing an auth code. Its `POST` verification path issues a session using `models.OTP`; token-hash lookup for `signup` and `recovery` uses different token categories, but generic email verification can consider both. A design based on signed AMR claims must therefore first prove the exact path, claim values, freshness, provider version and session/revocation semantics. Do not assume every recovery session contains a distinct `recovery` AMR.
- The token service associates authentication method claims with a session and calculates JWT AMR; that is a candidate for investigation, **not** a verified solution. A secure design must establish token signature/issuer/audience, user and session binding, freshness, one-time/replay semantics, and access restrictions in the presence of refresh, other sessions, password change and logout.
- An official `v2.197.0` Linux release exists, but its asset download redirected to a host unavailable in this sandbox. No Auth binary was obtained or run. Docker/Podman/Supabase CLI, Go, PostgreSQL and Chromium are not installed here. No hosted project, credentials, configuration or data was accessed. The attempted release asset fetch failed; it was not a successful provider test.

Source references: [`recover.go`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/recover.go), [`verify.go`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/verify.go), [`token.go`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/token.go), [`sessions.go`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/models/sessions.go), [`service.go`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/tokens/service.go).

## Test evidence and limitations

The added `tests/unit/supabase-pkce-sdk.test.ts` uses the **installed real SDK and SSR cookie adapter**, but replaces the Auth HTTP provider with a synthetic in-memory transport. With the SDK's experimental flow-ID setting enabled in the test only, it exercises two concurrent signup verifications out of order, missing slots and replay. It also demonstrates that the current default without the setting uses the latest verifier and that local metadata controls `redirectType`. Replay behavior belongs to the synthetic transport and must not be attributed to Supabase Auth. Callback argument/invalid-ID tests mock the server client.

Earlier auth-focused offline run: 13/13 hold checks and 41/41 unit tests passed in the network-isolated namespace/chroot. After the subsequent local audit changes, the same runner passed 13/13 hold checks and 50/50 unit tests. Lint, typecheck, the loopback-only isolated production build, `git diff --check`, and production-boundary checks (5/5) also passed. The optional encrypted-PDF fixture was absent and its eight structural probes were skipped. This is not a real Supabase Auth, browser or production test. No hosted database migration, scanner, Garage or financial logic was changed.

## Local provisioning investigation

- The official `v2.197.0` GitHub release lists `auth-v2.197.0-amd64.tar.xz`, size **9,897,464 bytes**, SHA-256 **b5c2991d1df760c9b099c1c2395a94bd1c2f83ed58901934921997179dc9f7ea**. Both the GitHub asset metadata and the release notes report that checksum; these are the same upstream publication, not independent signature or build attestation verification. The original download redirects to an inaccessible host in this environment. No archive was obtained.
- `scripts/verify-supabase-auth-archive.py` is an **offline inspector only**: it reads a regular, non-symlink file once, checks this exact pinned length and digest, then verifies a bounded XZ/tar structure and x86-64 ELF header without extracting or executing anything. Its synthetic tests do not verify that it accepts the actual release archive; its expected manifest is inferred from the upstream release Makefile. A checksum match alone does not establish runtime safety, deployed version, configuration or recovery behavior. It is not an installer or a sandbox.
- Building the pinned official source is a possible future route, not a tested alternative here. Its `go.mod` and Dockerfile require Go **1.27.0**; neither Go nor gccgo is installed, and its dependencies are not vendored. Go module/toolchain origins and download hosts would also need to be permitted and verified. We will not use an unverified third-party binary or bypass the sandbox network policy.
- Docker, Podman and the Supabase CLI are unavailable here. A separate disposable environment with an independently verified official release and PostgreSQL could run the provider without involving a hosted customer project. The full provider runner, provider-specific listener/egress checks, configuration, isolation and teardown must still be built and tested before any real-provider results can be claimed; the synthetic-only mail-capture scaffold below is not yet connected to Auth. Scanner/Garage no-NIC-VM requirements remain separate.
- Synthetic archive-verifier suite: **9/9** passed in a network namespace; no real Auth archive or provider was tested. No additional cloud configuration, production migrations or recovery changes were made.

## Synthetic mail-capture scaffold (local only)

`tests/supabase-auth/mail_capture.py` provides a bounded in-memory SMTP peer for a future test harness; it never opens a listener itself, forwards mail, writes mail to disk or logs message data. It accepts only `.test` envelope addresses, one recipient per message, bounded messages/queue/connections and a limited SMTP command set. Its verification-link parser accepts a single HTML link only if the Auth and callback URLs point to explicitly configured IPv4 loopback ports and expected paths; it does not fetch or follow redirects. The peer is not production SMTP, and compatibility with the real provider has **not** been established. Callers must not log mail, links, tokens or session data.

The socketpair suite runs with loopback down in the offline jail. Separately, `scripts/isolated-supabase-mail-tests.sh` creates a disposable user/mount/network/IPC/PID namespace and chroot, brings up loopback only, drops all capabilities and runs as a non-root UID with a clean environment; its synthetic TCP test checks no egress route, absence of host home/run/git, exactly one loopback listener during the test and none after, and successful jail deletion. The jail shares the host kernel and read-only system runtime; it is **not** the independently verified no-NIC VM required for scanner/Garage. These tests exercise a synthetic SMTP client only: no Auth binary, real provider emails or credentials were used. Full harness integration, safe archive staging/extraction, database preparation, provider startup/configuration and end-to-end recovery matrix remain open.
