# Customer duplicate policy review

**PASS local preservation; BLOCKED business decision and advisory UX.** Shared email and phone are legitimate (family, branch, shared finance desk); GSTIN can occur on more than one customer record and its uniqueness as row identity is not established. Enforcing any of the three as a database uniqueness constraint would reject legitimate data. Revised 013 uses **non-unique** per-business normalized lookup indexes, including archived records; it does not block, merge, delete or automatically warn. Advisory matching UI, thresholds and privacy authorization are **NOT IMPLEMENTED / NOT TESTED**. Future user-facing warning should require tenant access, avoid exposing PII in errors and always permit explicit separate records absent a reviewed contrary policy.

Index normalization: email `lower(btrim(email))`; phone digits only (no inferred country code); GSTIN `upper(btrim(gstin))`; null/empty normalized values excluded; archived records retained. Normalization is only lookup heuristic, not identity proof. Case folding/collation, Unicode, international phone equivalence and real data distribution remain **NOT TESTED**. `tests/database/run-tests.mjs` tests existing duplicates and invoice count survive migration, same-tenant case/whitespace shared email, formatted versus digit phone, case GSTIN and archived match, cross-tenant values, null and empty contact, different-key concurrency (two rows), same-key concurrency (one row), and same-key changed payload rejection. These synthetic checks do not measure index query performance or provider collation.

Idempotency request key prevents duplicate retries only for same tenant/key and payload; it does not deduplicate distinct keys and must not be described as one. `013` revokes direct authenticated INSERT, breaking legacy clients; see `customer-grant-compatibility.md`. `015` imposes separate GSTIN validation constraints, not uniqueness: special identifiers or existing nonstandard values may be blocked. Decision on GSTIN verification, legitimate identifiers, data remediation and collisions needs domain-owner review; no silent merge.
