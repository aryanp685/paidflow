# Customer create retry — local candidate

Migration `20261107001000_idempotent_customer_create.sql` and the matching app flow are **local only**. The migration has not been applied to hosted Supabase; the updated create UI requires that RPC and will fail there until an approved, safe, verified rollout. No financial RPC or proof/issuance hold was changed.

The candidate RPC checks active owner/admin/manager membership, normalizes and validates bounded fields, locks the business/request key, and atomically creates the customer, existing audit event and a private request record. Identical normalized requests return the original customer ID without another insert or audit; changed input with that key is rejected. Replays do not overwrite later customer edits or unarchive a customer. Idempotency is per business and request key, not a general duplicate-customer detector. Baseline roles still have direct `customers` INSERT rights: clients that bypass this RPC do not receive its retry guarantee. SQL validation is not a replacement for app email validation.

The UI retains the request key in same-tab session storage until confirmed success. It keeps form fields in component memory on returned errors, but not through reload, crash or navigation; reconstruct the exact same details for a safe retry. Starting a new key requires explicit acknowledgement after checking the customer list, and can still duplicate a previously committed customer. Other tabs/devices, different keys, direct writes, cleared storage and uncertain outcomes are not deduplicated. Confirmed replay is labeled as an earlier request, not a new creation.

The private request table retains the original customer fields (including contact information) for exact comparison, even if the customer is later edited. Direct authenticated/anonymous access is revoked, but privileged owners can access it. Data-minimization, retention, erasure, backup, key rotation and operational policy require review before production. Its FK also affects customer deletion. Do not remove request records prematurely and silently lose replay guarantees.

Synthetic isolated PostgreSQL with mock Supabase roles tested identical/mismatched and concurrent requests, role/tenant denial, private access, rollback of the customer/audit on injected failure and replay after edit/archive. Local app unit tests mock the provider. This is not a real Supabase Auth/PostgREST/privilege or browser acceptance test; actual provider rollout and independent review remain pending. Existing known baseline proof vulnerabilities remain a security acceptance failure, and both proof and issuance holds remain undeployed.
