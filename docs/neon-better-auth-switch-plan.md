## Free-tier and operational reality

On the official Neon plan page consulted for this plan, the Free tier is **$0/month within its allowances**: 100 CU-hours compute per project/month, 1 GB PostgreSQL storage per project (20 GB across projects), 5 GB public network transfer per project/month, scale-to-zero after 5 minutes, and a limited 6-hour instant-restore history. Exhausting compute or transfer suspends compute until reset or upgrade; exhausting storage can reject storage-increasing writes. Confirm current plan/availability and account eligibility at signup; terms can change. Free-tier suspension and short restore windows can interrupt payment operations and are not a financial-production SLA. Source: https://neon.com/docs/introduction/plans and https://neon.com/faqs/free-plan-limits-and-quotas.

The Better Auth framework itself is open source and self-hosted, but hosting, a transactional email provider, domain, optional managed services and future usage may cost money; a zero-cost overall stack is **not guaranteed**. Verification/reset email requires an actual sender integration and secure delivery. See https://better-auth.com/pricing and https://better-auth.com/docs/authentication/email-password. Managed Neon Better Auth is a different integration from this repository's self-hosted Better Auth lab; choosing it requires separate evaluation, not assumed compatibility.

Neon also advertises object storage on some plans/regions; eligibility, cost, versioning, retention, immutable-object and access properties must be confirmed before selection. As of the consulted Neon docs, its object-storage supported-region list includes Singapore but does not list Mumbai. Database region, object storage region, data residency, latency and price need explicit user/operational review: https://neon.com/docs/storage/overview. No storage provider or scanner is selected or provisioned.

## Proposed phases and explicit gates

1. **Confirm source and rollout mode.** Inventory the Vercel deployment and any existing real user/data source with separate approval. Decide whether this is a brand-new empty installation or a real migration. If user accounts, sessions or financial data exist, plan a one-time, independently tested export/identity mapping, verified reconciliation and cutover with a maintenance/read-only window. Never merge records on email alone, invent verified status, import password hashes without compatibility/security review, silently reset passwords, or dual-write. If the source is unknown, stop; do not create replacement accounts or migrate.
2. **Local-only production integration design.** Inventory Supabase browser/server imports, session checks, workspace/onboarding actions, queries/RPC contracts, middleware, error handling and database types. Specify one server-side Neon connection boundary and Better Auth integration for the production routes; keep the labs production-disabled and retain existing deployed behavior until approved cutover. No browser database credentials. Require trusted session validation, verified identity, active membership/role checks, secure cookie/origin/CSRF handling and tenant-scoped authorization on every operation. Define a neutral app interface so the cutover is atomic, not both identity systems writing simultaneously.
3. **Database/security design.** Create reviewed **new Neon-specific production migrations** from explicit schema requirements rather than copying lab or Supabase migrations. Verify managed Neon role/privilege capabilities and RLS policies; separate migration owner, authentication service and app runtime credentials, revoke PUBLIC/default grants, restrict ownership/BYPASSRLS/role membership, audit privileged operations and secure credential storage. Use server-derived UUID actor context in an explicit transaction with safe cleanup and verified pooling behavior; document that a stolen runtime credential or compromised server can impersonate users. Verify role/session safety against real Neon before claiming protection. Preserve financial constraints, idempotency, ledger/audit semantics, tenant isolation and integer currency arithmetic.
4. **Fail-closed proofs first.** Production-specific Neon schema must deny **all new non-NULL proof associations at the DB boundary**, including direct RPC/privileged writers within the permitted threat model, prior to exposing any financial workflow. Preserve NULL-proof payments, historical identical replays, voids and ledger/audit history. Additive migration and race tests must be separately approved and reviewed. Existing local storage-lab global grant/download/preview hold remains; no object upload, download, preview, scanner installation or real attachment is enabled. A future scanner requires byte-bound signed attestation, immutable object version, revocation, expiry, object-presence and storage-atomicity work described in `step-13-security-architecture.md`.
5. **Auth and mail security.** Adapt signup/login/logout, email verification, session expiration/revocation, rate limits, enumeration resistance, session fixation and tenant onboarding. Verify email sender, domain authentication, delivery/expiry/replay, callback allowlists and secret redaction. Keep password recovery disabled until its own real-provider tests and explicit approval; local synthetic SMTP/Better Auth tests do not establish production email safety. Plan for cookie changes and session invalidation on any real identity cutover.
6. **Testing and operations.** First use local tests only. After separate approval for isolated provider resources, run real Neon fresh-install/upgrade, role grants and RLS, connection pool reuse, transaction rollback, membership/revocation races, concurrent idempotency, cross-tenant direct SQL, fail-closed proof guard, mail and browser E2E, outage/quota/scale-to-zero and timeouts. Test backups/restores and reconciliation without real customer data. Pin runtime version (Vercel reports Node 26; earlier local compatibility tests used Node 22) and repeat lint, build, dependency/security and production-boundary checks. Verify quota alerts, support, ownership, cost and restore time objective before financial use.
7. **Decision and cutover only after approval.** Present exact provider/project/region, plan limits, expected costs, identity/data inventory, security evidence, maintenance impact, monitoring, restoration plan and customer communication. Obtain explicit approval separately for provisioning, migrations, production configuration and deployment. Cut over one source of truth; verify working no-proof payments, ledger and authorization. Keep Supabase rollback path read-only if there is an actual source.

## Rollback and financial consistency

Before cutover, restore the previous app configuration with no data movement. After any writes reach a new database, **do not simply flip back to a stale old database**: freeze writes, preserve both snapshots and audit evidence, reconcile payment/invoice/idempotency records, and approve a one-time reverse migration or forward-fix. Define downtime, recovery owner and test restoration in advance. If proof guard or role enforcement fails, deny proof attachment and keep feature unavailable; do not drop the guard to restore convenience. Failure to verify actual source, correct target, backups or ledger reconciliation blocks cutover.
