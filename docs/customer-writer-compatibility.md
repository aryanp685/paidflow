## Candidate versioned mutation interface

`supabase/migrations/20261107001600_customer_compatibility_review.sql` adds `public.patch_customer_if_version(uuid,uuid,integer,jsonb)`, SECURITY DEFINER with fixed search path and `require_business_role`; it locks the tenant/customer row with matching version then applies only a whitelist: name, contact_person, email, phone, whatsapp_phone, gstin, billing_address, shipping_address, state_code, payment_terms_days, credit_limit_paise, internal_notes, is_archived. Missing keys preserve old values; typed keys/unknown keys are rejected; table constraints still apply. Supplied changed GSTIN/state must meet 015's narrow rules. Unspecified old nonstandard values remain stored. The trigger increments version; stale/ABA fails with 40001; no-op still increments. The full patch API is **not wired to application archive/other field forms** and is not contract-compatible with old direct clients. It is a candidate, not proven safe for all input encodings, locks, volumes or provider owner roles. `tests/database/run-tests.mjs` tests supported field batch, stale, archive/unarchive, unknown key, invalid GSTIN, cross-tenant/viewer, concurrent cross-field writes.

**Trusted maintenance policy (proposed, not enforcement):** routine integrations must use an expected-version interface with an attributable active authorized user; `auth.uid()` absent does not pass the role-checking RPC. Unknown privileged direct writers are prohibited from normal concurrent operation, not silently considered safe. Any exceptional owner maintenance requires written approval, exclusive customer write freeze/quiescence, explicit tenant/row and version precondition, pre/post backup and verification, separately recorded human identity/reason, and review of activity log gaps. Trigger disabling permits unversioned and unaudited modifications and requires separate incident-grade controls. This policy cannot constrain a superuser and has **NOT TESTED** operational enforcement.

**Rollout:** inventory real grants, external writers and client versions; design compatible APIs for each consumer, deploy an expand/feature-gated sequence and prove old/new clients against actual provider in a separately authorized environment. Until coordinated retirement, revoking direct writes breaks clients; leaving them enabled permits lost updates. No broad UPDATE grant or deployment recommendation. Restore/rollback, function ownership, service role and privileged activities are **NOT TESTED**.

### 016 patch contract and adversarial outcomes

`tests/database/run-tests.mjs` tests run against actual disposable PostgreSQL, not PostgREST. `patch rejects malformed SQL and JSON inputs without modifying customer`: SQL NULL and JSON null/non-object/empty object, unknown key, forbidden null name/archive, wrong types, bad ranges and fractional integer rejected; explicit nullable email null clears it, allowed no-op increments version but does not create an update audit, and stale version returns 40001. `all customer patch fields use expected version and preserve unmentioned data` covers archived/unarchive, omitted nonstandard legacy GSTIN, unknown keys and role/tenant denial. `patch row lock forces a concurrent stale editor to wait and fail` actually holds the first transaction's row lock, observes second waiting, commits and verifies second returns 40001. `patch definer owner and grants are mock-only verified` checks SECURITY DEFINER, fixed search path, authenticated execute, anon/PUBLIC denied, local superuser/BYPASSRLS owner. Real PostgREST mapping, transaction behavior, owners/default grants and browser API **BLOCKED**.

The whitelist is not a comprehensive text/address validation policy: address JSON objects and notes have no explicit payload size bound, email/phone SQL validation differs from form validation, GSTIN raw patch must already be uppercase, and casts/constraints can return 22P02/23514 rather than a single sanitized error. A public client must not display raw SQL error details; no app consumer for patch exists. Explicitly including a grandfathered invalid GSTIN is rejected even if unchanged; omission preserves it. Oversized nested JSON, Unicode/collation, all extreme numeric encodings and real SQL error redaction are **NOT TESTED**. No RPC contract changed in Item 13.4.
