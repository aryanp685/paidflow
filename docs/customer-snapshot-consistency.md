**PASS bounded synthetic SQL snapshot; BLOCKED real-provider and browser acceptance.** No payment-recording or existing financial RPC contract changed. `supabase/migrations/20261107001600_customer_compatibility_review.sql` adds `public.customer_financial_snapshot(uuid,uuid,integer)`: one `STABLE` SQL statement, `SECURITY INVOKER`, scoped to tenant/customer under existing customer/invoice/payment RLS, execute granted only to authenticated. A customer with >1,000 issued invoices gets no partial outstanding total; payment navigation caps at 20,000.

## Alternatives and boundaries

A PostgREST multi-request REPEATABLE READ transaction is not available to the existing stateless client interface without new server connection/transaction machinery; independent HTTP requests do not share a snapshot. A separate replicated/read model adds refresh/lag and reconciliation complexity. A single invoker SQL RPC is the simplest local proposal. It guarantees a snapshot only for the data in that one response, not stability across pages or other UI queries; it does not reconcile invoices to payments as a contractual invariant or prove payments. Function owner/invoker role grants, RLS in real Supabase, PostgREST JSON/limits, performance and large count cost are **NOT TESTED**. 016 must be present before the updated detail page works; staged compatibility and rollback **NOT TESTED**.
