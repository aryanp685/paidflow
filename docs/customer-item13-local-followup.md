# Customer Item 13 follow-up — local acceptance criteria

Local candidate only; production/hosted access is prohibited. Status stays PARTIAL until evidence and independent acceptance exist.

1. **Concurrency:** a server-checked monotonic version changes on each customer update, including direct privileged updates; authenticated direct column updates are denied and a tenant/active-role-checked RPC requires the expected version. Stale and ABA versions fail, concurrent same-version writes yield one winner, and cross-tenant/unauthorized/direct bypass attempts fail. Privileged owners can still alter schema/triggers; rollout and old clients require review.
2. **Duplicates:** a documented deterministic per-tenant policy covers normalized email, phone and GSTIN, including archived rows, direct inserts, different request keys, and concurrent writes. Existing conflicts must never be silently merged, deleted or rewritten; migration must fail closed with an operator remediation plan that preserves historical references. Exact-match identifiers are not proof of identity; legitimate shared contact details may be rejected and require product review.
3. **Audit:** each successful insert and materially changed update yields one attributed customer event containing no contact values or old/new PII; failed/no-op changes yield no misleading edit event. Privileged or unauthenticated maintenance may have no authenticated actor and must not be misattributed. Existing history is not backfilled.
4. **Reconciliation:** independent fixture calculations compare customer issued-invoice totals less recorded, non-voided payments to stored invoice balances, covering partial, voided, archived and concurrent payments. Report failures and limits; no financial RPC changes.
5. **GST:** independently reviewed format, check digit and state validation tests distinguish standard identifiers from registration verification and unsupported classes. No tax compliance claim.
6. **Browser:** authenticated customer UI end-to-end for tenant isolation, workflows, stale edits and responsive/keyboard behavior on the Playwright-pinned browser with a safe local provider. Mocked browser/provider data are not real Supabase integration; absence of a compatible executable or local provider remains BLOCKED.

### 1. Versioned customer edits

- `20261107001200_customer_versioned_edits.sql` adds a positive integer `edit_version`, increments it in a `BEFORE UPDATE` trigger for every update (including privileged writers), and adds `update_customer_if_version`. The RPC locks active owner/admin/manager membership, tenant-scopes the update, requires the current version and rejects absent/archived/stale targets. Authenticated direct UPDATE column grants are revoked. The server action sends the form version and shows a generic stale/access error; it no longer relies on value-snapshot CAS. Changed rows return a new version. Integer overflow fails rather than wrapping.
- **SYNTHETIC:** SQL tests reject authenticated direct updates and cross-tenant/role misuse, exercise A→B→A with old version, show an ordinary privileged update advances the version, and exercise simultaneous same-version edits with exactly one winner. This does not prove real Supabase/PostgREST grants, delegated roles, superuser behavior, or that privileged writers themselves use CAS; owners can bypass/disable triggers. No claim of protection against a malicious schema owner.
- **Compatibility:** revoking direct customer UPDATE intentionally breaks older API clients, including direct edits of address, notes and archive flags; the RPC only supports the six customer form fields and cannot archive. This is an explicit migration compatibility issue, not a seamless additive rollout. New app edit requires the new column/RPC; missing migrations fail closed. Inventory all writers and plan atomic transition before any separate authorization. Test actual provider grants and elevated service paths independently.

### 2. Duplicate policy

- `20261107001300_customer_duplicate_policy.sql` rejects same-tenant, nonempty exact normalized email (`lower(btrim)`), digit-only phone, or uppercase/trimmed GSTIN across **active and archived** records using three unique indexes. Same normalized identifier is allowed in another tenant; records without these identifiers and same names can coexist. Formatting/case normalization is not identity verification: phone country codes, extensions, Unicode/email aliases and equivalent real-world identities may not normalize together; legitimately shared phone/email or GSTIN can be rejected. Product/operational approval and a privacy-safe exception workflow are unresolved.
- Both idempotent create and edit RPCs convert unique-index errors to a generic message without identifier details; authenticated direct INSERT is revoked so normal callers must use the idempotent RPC. Authenticated direct UPDATE was revoked by 012. **SYNTHETIC:** same-key replay works, different-key duplicates and archived reservations fail, different-tenant succeeds, empty identifiers work, direct insertion fails, simultaneous competing keys yield one row, and conflicting edits leave version/audit unchanged. Privileged clients may still see native constraint details; logs and administrative privilege/retention policies require review.
- Migration preflight detects existing collisions and aborts with a generic error, no automatic merge, deletion, relabeling or financial-reference change. A synthetic legacy-collision test proves rollback and row preservation. Test-only synthetic fixture cleanup is done in the disposable database after that test; it is **not** a real-data remediation procedure. Before any proposed deployment, conduct privacy-restricted duplicate inventory, obtain human decisions for shared identifiers and archived historical records, and design non-destructive resolution. A restored index may also fail if data changes during preparation; review locks, index build time, concurrent writes and migration transaction behavior on the actual provider. Do not merely discard duplicates or remove constraints to force a pass.

### 3. Customer audit

Historical updates before this trigger are not backfilled; no end-to-end audit immutability, retention, real-provider actor authenticity, privileged tampering protection or full related-invoice/payment timeline is claimed.

### 4. Independent ledger fixture

- A disposable PostgreSQL fixture creates three separately issued invoices, records partial payments, voids one, runs two simultaneous successful payments, records payment on a third invoice and marks it archived. Separate JavaScript `BigInt` arithmetic reads invoice totals and individual recorded/voided payment rows, independently calculates each balance, and compares it to cached `paid_paise`/`balance_paise` and the customer summary query. Active outstanding is **22,000 paise**; including the archived invoice it is **47,000 paise**; the voided record is retained but excluded. This is actual independent calculation against synthetic local ledger rows, not merely a mock or a real-bank/provider reconciliation.
- Display continues to exclude archived invoices, and queries are not one transaction-wide snapshot. Whether archived unpaid invoices should be excluded, performance/limits, drift detection in the actual UI, reconciliation/restore against real historical data and accounting review are open. The fixture does not change financial RPCs or holds.

### 5. GST identifier review

- `20261107001500_customer_gstin_validation.sql` and the app now check standard PAN-based shape, base-36 check digit, supported state prefixes 01–38, and matching supplied state. This is a deliberately narrow implementation policy, **not** an authoritative state allocation list, a registry check, proof of ownership, tax/legal compliance, or support for special GST identifiers. Review with domain experts and official sources before production; legitimate identifiers outside this subset may be rejected. SQL-only same-key replay of a previously accepted legacy payload is preserved before new stricter checks; however the current app validation can reject such legacy inputs before they reach the replay RPC, so ambiguous old retries still need a safe client migration/compatibility plan. Existing legacy rows are not silently rewritten, and editing them may require correction.
- Synthetic cross-language vectors cover prefixes 01, 27, 29 and 38, invalid checksum/pattern/00 prefix, state mismatch, and SQL create/edit rejection. These are implementation examples, not independent authoritative registration or tax-law validation.
