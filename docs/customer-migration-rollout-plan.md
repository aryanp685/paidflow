# Item 13.4 — customer migration expand-and-contract plan

**Status: DESIGN ONLY / NOT APPROVED.** This is not an instruction or authorization to deploy. The current proposals 012–016 combine expansion and incompatible revocation and are **not a safe staged migration plan as written**. No production or provider inspection occurred. No broad direct UPDATE grants should be added. Existing financial/payment/proof contracts and holds remain unchanged.

## Preconditions and inventory gate

- Deployment owner must inventory every app version, direct PostgREST/SQL/mobile/integration/import/background writer and field, service role, privileges/inheritance, deployment owner, notification and support contacts, long-lived clients and legacy retry behavior. Repository findings and unknowns: `customer-writer-compatibility.md`. No unknown or unowned consumer may be treated as retired. Establish privacy-safe, separately reviewed detection/telemetry (no contact values, secrets or raw request payloads), ownership and a defined observation period across the longest client lifecycle; exact thresholds are a business/operations decision, not verified here.
- Independently review legacy duplicates, GSTIN/special identifiers, version overflow, 010 PII ledger, index build cost and locks, real definer owner/search path/grants/RLS, validation errors and API shape. No actual provider grant or ownership check was authorized.
- Establish encrypted backup with documented restore point, retention, restore drills in a separately authorized isolated synthetic environment, verified invoice/payment/customer/audit/request-key referential integrity and reconciliation. Freeze/backup planning must include irreversible post-backup writes. **NOT TESTED**.

## Safe sequencing proposal

1. **Expand:** redesign/split draft 012–016 so additive version/trigger, audit and new interfaces can exist without silently revoking old clients. Add new explicit full-field expected-version API (including archive/unarchive) with validated error contract, test provider ownership and grant surface, data-preserving upgrade and rollback. Client feature flag defaults OFF until the functions exist and compatible. *During coexistence direct legacy writes can still bypass CAS:* this is a known degraded phase, **not security acceptance**. Existing 012/013 as written do not implement this nonbreaking phase.
2. **Migrate consumers:** update and inventory all writers to pass expected versions; add application actions/UI for currently unsupported archive/unarchive and other fields if product supports them. Update clients to handle 40001 reload/review, invalid legacy GSTIN and no-op version change. Restrict trusted maintenance/import writers separately; verify no trigger-disable route for application identities. Enable flag per consumer only after the schema and API compatibility are proven.
3. **Retire legacy:** deployment owner explicitly approves retirement after observing all known clients and external integrations, validating no remaining legacy writes for the full observation period, having a comms/rollback plan and resolving unknown consumers. A controlled write freeze or maintenance cutover may be necessary: a flag alone cannot prevent a direct writer racing a new CAS writer. Verify no writer bypass, then contract direct grants in a separately authorized migration. No observation period, feature flag or retirement gate exists here.
4. **Prove/review:** test old/new clients at each phase and interrupted upgrade, provider RLS/PostgREST, ordinary and privileged roles, lock/contention/load, backup restoration and rollback. A rollback to legacy grants reintroduces lost-update risk; label degraded and control writes, rather than claiming CAS.

## Trusted maintenance and recovery

Normal background/import paths must use a version-aware authorized identity. Exceptional privileged direct DML requires approved ticket, named operator, maintenance/write freeze, per-row tenant/version preconditions, independent change evidence, pre/post validation and review. Owners can bypass these controls; enforcement, independent audit sink and breach detection remain **NOT TESTED**. If rollback is necessary, stop writes, assess what has committed since backup, preserve request ledger, versions, events and financial history, route only to compatible clients and test restoration/reconciliation before any return. Do not blindly drop version/audit columns or restore a backup over newer financial data. Exact rollback/recovery SQL is **NOT TESTED** and intentionally not provided.
