## Ordered closure criteria (proposal)

1. **EXTERNAL OWNER CONFIRMATION REQUIRED:** sign a complete consumer/version/role/field/owner matrix, including manual and batch workflows, longest offline/client update cycle and support contacts. Select compatibility period **W** no shorter than the approved maximum supported client lifecycle; exact W is not determined here. Approve retirement and write-freeze authority.
2. **NOT TESTED:** implement approved per-consumer, privacy-safe telemetry for legacy versus versioned writes: coarse client/version/path/role classification, counters/timestamps, redacted failure category and retention; exclude names, emails, phone, GSTIN, raw payload, tokens and secrets. Independently cover direct gateway/database/privileged paths and detect blind spots/outages. Record telemetry completeness, not just zero counts.
3. **NOT TESTED:** expand using additive API plus explicit feature flags default OFF; prove client/schema compatibility both directions. Cover all supported fields and archive/unarchive with expected-version checks and defined errors. During any period old direct UPDATE remains usable, it can bypass CAS: report degraded, never universal CAS.
4. **EXTERNAL OWNER CONFIRMATION REQUIRED:** every identified consumer signs migration or retirement; monitoring has zero unaccounted legacy/direct writes throughout W and no monitoring gaps, with independently verified completeness. Zero telemetry alone is insufficient. Unknown external sources, stale offline clients or unknown jobs block cutover.
5. **NOT TESTED / EXTERNAL OWNER CONFIRMATION REQUIRED:** controlled write freeze (or a proven equivalent) and final drain, no concurrent direct writers, backup/restore and rollback readiness, then separately approved contract/revoke of legacy grants. Verify direct SQL/HTTP denial and new versioned success without restoring broad UPDATE. Publish no passwords, personal tokens or credentials in evidence.
6. **BLOCKED:** recovery runbook must cover writes after cutover; freeze, preserve both histories, version/request-key/audit/financial data, reconcile and independently approve forward fix or reverse migration. Flipping to an older DB or dropping versions/audits is not a safe rollback. No production action authorized here.
