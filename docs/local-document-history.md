# Local document activity and attributable-denial views

This branch adds **local-lab-only** owner/admin views of the latest 100 document lifecycle events and latest 100 attributable denial events. Neither is a complete security audit or a production feature. Download and preview remain disabled. No scanner, malware verdict, successful download, Garage pilot, hosted migration or cloud change is implied.

## Lifecycle events

The additive lab migration `storage-lab/migrations/20261107050000_document_history_reader.sql` creates a fixed-projection `SECURITY DEFINER` reader. It checks and locks the caller's active owner/admin membership before reading events, filters by authorized tenant, restricts event kinds, and returns IDs, action and timestamp only. It does not return event metadata, filenames, object paths, content, cookies, tokens or URLs. Only the trusted local server role can execute it; the actor comes from verified session context.

## Attributable denial events

The additive lab migration `storage-lab/migrations/20261107060000_tenant_denial_reader.sql` adds nullable business/document IDs to the private denial sink and an owner/admin tenant-scoped reader. Existing unattributed rows remain unattributed. The application supplies a target to the writer only **after** an authenticated operation has authorized that target. The writer rechecks authorization in a separate transaction: if access has been revoked or the target is unauthorized, the event persists without target or tenant. The reader returns only events already attributed to its authorized tenant; it does not expose unassigned events. Grant/preview/download hold failures after a successful read lock, upload validation failures after upload authorization, and delete failures after delete authorization can therefore appear. No untrusted request text or metadata is recorded.

The view is intentionally incomplete: anonymous, origin failures, missing/expired sessions, invalid grants, cross-tenant or other pre-authorization denials, route-level validation before delegation, and older unattributed events cannot safely be associated and are omitted. A denied event means the request did not complete, not necessarily that a permission check failed. Audit write failure denies the protected operation but cannot guarantee a record exists. The reader exposes IDs/action/reason/time only; no signed URLs, tokens, cookies, filenames, object paths or file content. It does not show scan outcomes or successful downloads.

Both APIs are disabled in production and return `no-store`; UI components discard stale results on workspace switch. Each view shows at most 100 rows and indicates truncation; pagination is not implemented.

**Important limits:** Existing `activity_logs` policies allow active members to read their own tenant's activity through the trusted runtime role; the new history function restricts its **reader/API**, not every possible SQL use of that older table. Private denial records remain inaccessible for direct runtime SELECT/UPDATE/DELETE, but narrow writer functions trust the server-set actor. A compromised runtime can impersonate actors or fabricate events, and DB owners can alter logs; neither view is tamper-proof. Cross-tenant result contents are checked, but timing-side-channel resistance has not been proven. Audit retention, durable outage/backpressure, rate limiting, alerting, comprehensive event coverage, role policy review, cursor pagination, real-browser tests, log leakage testing and production/Supabase integration remain open. Do not apply these local-lab migrations to production.

## Synthetic verification

Actual local PostgreSQL + Better Auth tests cover owner/admin, viewer/cross-tenant rejection, anonymous/expired/suspended denial, role changes, membership-lock serialization, post-authorization attribution, stripping after permission changes, denial-writer failure, whitelist/projection and injected-secret exclusion, 100-row truncation, and additive upgrade preservation. Integration teardown completed successfully. The API/UI tests use mocks and do not establish real-browser or production behavior. The PostgreSQL test jail has no external route, inherited credentials, host home/run sockets, Git or effective capabilities, but shares the host kernel/read-only runtime and is not the no-NIC VM required for scanner/Garage pilots.
