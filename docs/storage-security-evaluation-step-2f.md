# Step 2F — Storage security and malware-scanning evaluation

**Evaluation date:** 7 November 2026. **Decision:** evaluation only; no storage replacement, scanner installation, deployment, paid service, cloud connection, production credentials, or customer documents. This is not a production security certification.

**Most important finding:** the current lab permits an authorized download of `structurally_valid_unscanned` files. Structural parsing is not antivirus, and the proposed fail-closed scanning requirement is **not met**. An offline synthetic EICAR-marker PNG passed the existing structural check. That probe does not run an antivirus, and does not prove what a real scanner detects. Complete document-access auditing is also **not implemented**.

### Named security findings and uncertainty

* Garage v2.5.0 release notes reported fixes for malformed-URL UTF-8 panic and restrictive owner permissions for bucket lifecycle configuration ([release-note mirror](https://github.com/Makifun/nixos/pull/205)). The public GitHub mirror advisory API returned no entries; absence of published entries is **not** proof of no vulnerabilities or a complete advisory search. The source project is hosted outside GitHub. The lifecycle change is breaking and its migration implications must be checked.
* SeaweedFS [GHSA-5fx4-c9qp-36jc](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-5fx4-c9qp-36jc), critical, describes unauthenticated S3 gRPC IAM identity mutation through reachable interfaces; advisory API lists `<=4.45`. [GHSA-qmx6-fpcw-q3xg](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-qmx6-fpcw-q3xg) reports POST Object bypassing bucket policies and cross-identity overwrite, listing `<=4.45`. [CVE-2026-55873 / GHSA-hgpf-8634-g44c](https://github.com/seaweedfs/seaweedfs/security/advisories/GHSA-hgpf-8634-g44c) reports S3Tables inventory disclosure in 4.08–4.33, fixed in 4.34. Although 4.52 is outside the listed ranges, the first two advisory API records did not supply a first patched release; independently verify fix commits, release backports and current advisories rather than inferring security from version numbers. Disable unneeded surfaces and isolate internal ports regardless.
* RustFS [CVE-2026-27607](https://github.com/rustfs/rustfs/security/advisories/GHSA-w5fh-f8xh-5x3p) concerns old alpha presigned POST policy-condition enforcement; [GHSA-3ppv-fx5m-m749](https://github.com/rustfs/rustfs/security/advisories/GHSA-3ppv-fx5m-m749) concerns historical-version reads using the wrong authorization action in versions before beta.11. More recent [GHSA-rhg6-jrf2-29c4](https://github.com/rustfs/rustfs/security/advisories/GHSA-rhg6-jrf2-29c4) reports alternate protocols bypassing policy conditions through 1.0.1. These listed ranges do not establish a defect in 1.0.4; they do justify checking fix commits and disabling extra protocols. Security history is not an exhaustive audit or comparable vulnerability count.
* API descriptions are vendor claims, not tests here. Garage's lack of policy/versioning affects design: **do not assume** a shared bucket prefix, version ID or S3 public-block policy itself enforces tenant isolation. Separate restricted buckets/keys plus a trusted access service and database authorization need verification. If immutable version identities are required, use a provider supporting them or cryptographically verified immutable unique keys with tightly restricted overwrite/delete permissions.

## B. Recommendation and evaluation gates

**Recommend Garage as the first later local candidate**, not an approved replacement: a limited S3 surface and separate bucket/key grants are suitable for a small local lab, subject to its AGPL license, Linux-VM overhead, no S3 object versioning and required application behavior. SeaweedFS is a meaningful second choice if a native macOS ARM64 binary or Apache license is important, but its authentication defaults and numerous internal interfaces demand more hardening. RustFS is an alternative when S3 policy/public-block behavior is needed; its wider feature set and advisory history deserve thorough tests. Choose only after explicit approval and compatibility measurements. Never silently remove S3rver from the lockfile.

After separate permission, obtain pinned artifacts from upstream, verify checksums and supported architectures, review current advisories and license, use isolated disposable data, random credentials and no publicly accessible services. Run equivalent AWS SDK tests for unsigned and bad-signature requests; ungranted buckets and keys; cross-tenant PUT/GET/DELETE/LIST; normal PUT/GET/DELETE; multipart create/upload/complete/abort, expiry and cleanup; presigned GET/PUT, expiration and tampering; endpoint/region/path handling and size limits. Include the local app's exact request shapes. Measure idle, peak uploads, parallel scans, signature reload, swap, time and disk on the actual 8 GB Mac alongside Next and PostgreSQL; apply explicit acceptance thresholds agreed beforehand. Do not claim an emulator duplicates R2 policy, consistency, transport or implementation behavior.

## C. Proposed scanner architecture — not implemented

[ClamAV](https://docs.clamav.net/) is a maintained, free/local candidate; GitHub releases show 1.5.4 and 1.4.6 on 7 August 2026 ([upstream](https://github.com/Cisco-Talos/clamav/releases)). Select a supported version based on the current upstream lifecycle/advisories when approved. Fresh signatures require a separately approved update path; no definitions were downloaded or scanner run. The [installation guidance](https://docs.clamav.net/manual/Installing.html) recommends at least 3 GiB RAM and 5 GiB disk; [Docker guidance](https://docs.clamav.net/manual/Installing/Docker.html) calls for 3 GiB minimum/4 GiB preferred and warns a signature reload may briefly double engine memory. These are vendor guidance, not our measurements: an 8 GB Mac running the OS, VM, Next and PostgreSQL may struggle. Compare a native Apple Silicon build with an isolated container only after approval and measure peak memory; do not assume a free local engine has zero operational cost or zero false negatives.

Proposed flow:
1. Authenticate and authorize tenant/role **before** accepting work; enforce request limits at the edge and during streaming, use server-generated unpredictable keys and per-tenant quotas. Store only in a private quarantine bucket inaccessible to browsers/download credentials; quarantine and approved locations must be distinct authorization domains. Encrypted/unsupported/password-protected, malformed and disallowed type files are rejected or remain inaccessible for explicit re-upload/review; never send passwords to logs or scanner jobs. No files are executed.
2. Create an idempotent database document and durable scan job with tenant, actor, object identity, expected length and SHA-256. Validate structure and type conservatively without calling it malware detection. Prefer immutable object identity and separately restricted roles; prevent replacement during scan/promotion. Object keys and hashes alone do not grant access.
3. A least-privilege isolated worker reads exact quarantine bytes, hashes as it streams, uses a private authenticated/OS-permissioned Unix socket to an isolated `clamd` where practical, or tightly authenticated/isolated transport otherwise. Do not expose raw clamd TCP publicly. Restrict scanner network/filesystem, resources, process identity and outbound access; definition update is a separate controlled component. Deny arbitrary local paths, symlinks and execution. Limit queue size, concurrency, retries, elapsed time, memory, input bytes, decompressed work, recursion and archive members. Treat limit/incomplete alerts, unsupported or encrypted content, stale/missing signatures, malformed or ambiguous responses, worker crash, disconnect and timeout as **unknown/error**, not pass; prevent download and payment-proof verification. Set and verify `StreamMaxLength`, `MaxFileSize`, `MaxScanSize`, recursion and alert settings against app limits. ClamAV's [scanning guidance](https://docs.clamav.net/manual/Usage/Scanning.html) warns that oversized files can be skipped; [INSTREAM protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html) has its own stream limit. `AlertExceedsMax` is useful but does not itself establish complete scanning.
4. Attestation records the exact SHA-256, byte length, immutable object identity/version where available, tenant/document, scanner engine and signature database versions/digests, policy version, start/end, outcome (`no_signature_detected`, `detected`, `incomplete`, `error`) and audit correlation; optionally sign/MAC the canonical attestation with a server-protected key. Bind results to the actual scanned byte stream, not user-supplied metadata. Ensure a signature reload cannot make the recorded version ambiguous: scan against a pinned generation/snapshot or obtain an engine-supported unambiguous result; otherwise mark inconclusive. Never label a file malware-free.
5. On a complete non-detection, independently verify digest/length and immutable identity, copy/promote into a private approved store with server-only credentials and verify the promoted bytes. Commit state/attestation under a row lock and check generation, identity and policy again before making it downloadable. DB/storage are non-atomic: durable pending states, an outbox, idempotent retry, reconciliation and orphan cleanup are required for all crash boundaries. Only a trusted scanner path can set the downloadable/verified state; privileged manual test fixtures are not scanner attestations.
6. When signature database or policy generation changes, mark previously accepted objects stale, block new grants and downloads until a current attestation is obtained, queue rescans with concurrency/backpressure, and record outcomes. Each download must recheck active membership, current status, attestation freshness and object identity/hash; revoke outstanding grants promptly. Historical payment/ledger records must remain intact even if a previously linked proof is later flagged: access revocation and historical retention are separate. Stale rescan and retention policies require product/security approval.

## D. Proposed history-preserving audit design — not implemented

Existing events live in `public.activity_logs`, with tenant RLS and database event triggers/functions. Today `document.registered` is inserted on registration, `document.uploaded` on structural completion, `document.revoked` on successful revocation and `document.deleted` on completed deletion; stale quarantine may produce `document.upload_abandoned`. `storage_transition` intentionally emits no event when entering `deleting`. Inspection occurs before registration, so failed structural validation currently produces no document event. `grant` and `download` emit no document-access events; scanner events do not exist. Source: `neon/migrations/20261107000500_indexes_and_audit.sql`, `storage-lab/migrations/20261107030000_proof_lifecycle_and_scan_state.sql`, `storage-lab/core.mjs`. Existing successful revocation is a DB transition; no complete scanner-initiated revocation flow exists.

| Required event | Existing observed source behavior | Future event |
|---|---|---|
| Upload initiated | `document.registered` only after auth and successful structural validation; not every attempt | `document.upload_initiated`, including failed/aborted attempts |
| Upload completed | `document.uploaded` after structural check, **unscanned** | `document.upload_completed`, explicitly distinguish receipt, structural status and scan status |
| Structural failure | No event; validation precedes registration | `document.validation_failed` with allowlisted reason |
| Scan pass/failure | No scanner or events | `document.scan_passed`, `document.scan_detected`, `document.scan_failed` / incomplete, plus versions and rescan |
| Authorized download | No access event | `document.download_authorized` and delivery result where feasible |
| Denied download / cross-tenant denial | No access-denial event | `document.download_denied` and `document.cross_tenant_denied`, with non-enumerating external response |
| Revocation | `document.revoked` for successful transition | Preserve event; include cause, actor/system and scan generation without deleting history |
| Deletion attempted | No event on transition to `deleting` or failed store delete | `document.deletion_attempted` and `document.deletion_failed`, correlation and retry count |
| Deletion completed | `document.deleted` after successful delete | `document.deletion_completed`; distinguish accepted deletion from verified object absence |

Design append-only, server-side event IDs, UTC timestamps, typed event/version, derived tenant ID where legitimately established, actor ID or explicitly anonymous/system, document ID only when safely resolved, operation/correlation/idempotency IDs, action, allowlisted outcome/reason, and non-sensitive area/size/type plus scanner generation where appropriate. Never store contents, signed URLs, tokens, authorization headers, session IDs/cookies, passwords, S3 credentials, free-form user text, unsafe filenames or unredacted exceptions; don't log a hash as a substitute for a secret unless specifically justified. Redact HTTP, database and provider logs too. Enforce append-only privileges, RLS and tenant-safe readers; back up and retain history according to an approved policy. Restrict event access and monitor audit failures. Separate a restricted security/abuse sink for anonymous/unknown-tenant or cross-tenant probes: don't trust the requested tenant or reveal another tenant's existence/metadata to an attacker or their tenant. Rate-limit and aggregate abusive denial events without silently losing required evidence.

Successful business-state changes and their audit/outbox records should commit atomically. Denials and failed transactions need a separate durable, least-privilege append mechanism **outside the rolled-back transaction**; agree whether an audit-store failure blocks sensitive operations, and avoid logging secrets while reporting that failure. Delivery and object storage cannot be atomically committed with PostgreSQL: use idempotent event IDs and an outbox, retry, reconciliation and explicit attempted/completed semantics. Test RLS, append-only behavior, crash/retry, unavailable sink, metadata redaction and every event path. This is a design, not evidence that the current system has those guarantees.

## G. Blockers and residual risk

1. No scanner, actual malicious-file detection, timeout/unavailable fail-closed behavior, scanner attestation, signature freshness or automatic rescan. Unscanned lab downloads are permitted.
2. Access/denial/validation/attempt audit events and a durable denial path are incomplete. Historical leakage assertions cover only tested paths. Audit store, application, provider and access logs need a redaction policy.
3. Current S3rver is archived, vulnerable and not SigV4-verified; the token guard is not a vulnerability patch or a network boundary. Lab HTTP listener Host checks can be spoofed. Do not publicly expose the lab; establish network isolation before running it.
4. No fresh Step 2F DB/browser/integration results, actual scanner detection, candidate-store compatibility, ARM Mac benchmark, R2 or Neon test. A single-node emulator cannot establish production storage durability or access policies.
5. PostgreSQL and object store operations are non-atomic; retries and reconciliation must handle crash/race boundaries. The runtime actor GUC depends on a trusted application and cannot defend against arbitrary SQL using compromised runtime credentials; privileged database roles bypass RLS.
6. Other previously documented blockers remain: in-memory lab recovery links, no production mail/rate limiting/MFA, legacy Supabase recovery marker not tightly bound to recovery-session type, and no real Supabase/Neon/R2 validation. Existing implementations and migrations remain preserved.

## H. Proposed implementation sequence — requires separate approval

1. Agree security/audit acceptance criteria, licensing, resource budget and an isolated local test environment; explicitly authorize any new artifacts or processes. Rerun all existing storage, auth, browser, upgrade and integration regressions without publicly exposing listeners, including missing anonymous/cross-tenant download assertions.
2. Pilot pinned Garage locally, measure actual Apple Silicon resource peaks and run the compatibility/security gates in B; compare SeaweedFS/RustFS if Garage fails. Do not change the existing emulator until a replacement passes and rollback is documented.
3. Design additive schema/permissions and append-only audit/outbox with testable event coverage and redaction. Preserve all existing migrations, proof history and payment RPC behavior; plan explicit migration and rollback.
4. With separate scanner-installation approval, prototype isolated ClamAV and signature updates; test EICAR, encrypted/unsupported files, limits, stale definitions, unavailable/timeout/incomplete scans and peak RAM. Do not execute uploaded files or use customer documents.
5. Implement private quarantine, scanning, immutable byte-bound attestation, promotion and reconciliation; add fail-closed download/proof controls and rescan invalidation. Test races, retries, unauthorized access and audit completeness against actual scanner and store.
6. Review dependency fixes with evidence, rerun complete local suites and security review, document unresolved blockers and request the next approval. No cloud provisioning or deployment in this step.
