# Non-GST invoice draft — local candidate

Status: **local implementation only, not production-ready or deployed**. `supabase/migrations/20261107000800_non_gst_invoice_draft.sql` is an additive candidate, tested against disposable PostgreSQL with mock Supabase auth. The hosted Paidflow project has not received this or any earlier migration. Migration-history reconciliation and a reviewed, atomic proof hold remain blockers. No financial RPC or prior migration was modified.

The new form supports only non-GST draft creation: customer, dates, 1–20 description/quantity/unit-price lines. GST, discounts, shipping, additional charges, draft editing, issuance, sending and payment operations are not implemented in this UI. The underlying pre-existing `issue_invoice` RPC is granted to authenticated users in the baseline schema: absence of an issue button **does not block direct RPC calls**. Candidate migration 009 adds a local-tested database issuance hold, but has not been deployed. No release should proceed until issuance authorization and financial/GST behavior receive separate review.

The server derives tenant and role from a verified workspace, checks the selected workspace has not changed, and converts rupees to integer paise without floating-point money calculations. The SECURITY DEFINER RPC rechecks membership, validates payload and amounts, locks the customer against concurrent archive, generates the invoice number and saves invoice, line items, idempotency request and audit in one database transaction. An identical request key and payload replays without another invoice; a different payload with the same key fails. The UI stores the request key per workspace in session storage so a retry in the same tab can be deduplicated. It does **not** save form input: after an interrupted request or refresh the user must re-enter exactly the same details. A new tab, cleared session storage or a deliberately new request key cannot prevent duplicate invoices; users must check the invoice list before submitting a new request after uncertainty.

The private idempotency table stores the request payload (including line descriptions); runtime table access is revoked, but operator access, audit, retention and privacy policy require production review. The financial rounding rule is positive quantity × integer paise, rounded to the nearest paise (half up); total is the sum of rounded line totals. This does not establish GST correctness or tax compliance.

Verification: seven new disposable PostgreSQL checks cover rounding/line totals, idempotent replay, mismatched payload, invalid inputs, foreign tenant and restricted roles, injected atomic rollback, simultaneous identical and conflicting retries, and private-table permissions. Fresh local schema creation also passes with the candidate migration. Unit tests cover validation, exact conversion, tenant/role checks, error handling and session-key reuse. These tests do not establish real Supabase Auth, PostgREST, browser/provider behavior, hosted grants, production availability, or security against a privileged DB operator. The existing proof and recovery holds remain.
