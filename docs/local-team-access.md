# Local team access candidate

The local workspace now has an owner/admin-only team screen listing tenant-scoped existing memberships, including suspended members. Because the baseline `profiles` policy only permits users to read their own profile, the screen intentionally shows opaque user IDs rather than inventing names or emails. Check the ID before changing access. Non-admin direct page visits are rejected. This page restriction is not a confidentiality boundary: the baseline permits active members to read tenant membership rows through the database API.

Owner and admin can use the candidate compare-and-set RPC to change other members' role/status with explicit confirmation; admins cannot modify admins or assign admin, neither can change an owner or themselves, and ownership transfer is not supported. The RPC validates the live actor and target under locks. It compares the supplied expected role/status to the current role/status before changing anything, and a successful change triggers the existing member audit. The UI advises reload after errors because a response may be ambiguous. The new function checks only the current **values**, not a version counter: an intervening change that later returns to the original values (ABA) is not detected.

**Important:** the existing `set_member_access` RPC remains granted to authenticated users. Callers able to use it can bypass this candidate's compare-and-set semantics, though the old RPC still enforces its own role/tenant checks. This local addition is therefore not a database-wide concurrency guarantee. Retiring or changing that API requires a reviewed compatibility and migration plan, not a silent grant change. Direct baseline membership reads and existing invite-creation RPC exposure also require provider-level review. Creating an invitation is not the same as delivering or accepting one; no invitations, email delivery, acceptance, ownership transfer, membership deletion or profile lookup are implemented here.

Candidate migration 011 and the UI are **not deployed**. The UI action requires 011 and will fail safely if it is missing. Mock-Supabase PostgreSQL tests cover role boundaries, stale values, no-op auditing and simultaneous changes; app tests mock the provider. Real Auth/PostgREST, session revocation, hosted permissions, invitation security, privilege drift, ABA, audit retention and multi-device behavior require independent review and real-provider tests. Security acceptance remains blocked by the separately documented base proof vulnerabilities; issuance and proof holds are undeployed. No UI polish or production release was performed.
