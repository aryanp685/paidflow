# Evidence vault: informational hold

The workspace evidence page is a local **status page only**. It does not retrieve document metadata, read file bytes, call a storage API, upload, attach, preview or download. It does not assert that historical evidence is absent, scanned or safe. The normal workspace layout verifies session and active membership; the page itself has no document operation. The sidebar continues to label the vault as unavailable.

This UI is not a security boundary. The checked-in base Supabase schema permits authenticated callers with certain roles to insert document metadata and permits direct use of the payment RPC with an unscanned proof reference; synthetic tests demonstrate those gaps. The separate deny migration 007 is local and undeployed, and only blocks new payment-proof associations, not all metadata or object access. It does not verify scans, secure a storage bucket, prevent privileged bypass, or protect a hosted project until actually applied and verified. No assumption about historic objects or URLs should be made.

Enabling actual evidence requires, at minimum, approved and verified provider-specific access controls for every path (including direct API/RPC), private and immutable object/version handling, trustworthy scanning of the exact bytes with failure/timeout/revocation hold, scoped authorization, audit, safe migration of historic records, outage/race testing, and independent security review. Scanner installation, proof access and cloud changes remain outside this step. See `step-13-security-architecture.md` and `docs/local-proof-attachment-hold.md` for threat model, known gaps and release gates.
